**Defect found and fixed beyond the section text (C2, deeper than described):** the
`onConflictDoNothing({ target: projects.slug })` guard that §01 inherited from `create-lead-task.ts`
and labelled "conflict-safe ✅" **never worked**. `idx_projects_slug` is a *partial* unique index
(`UNIQUE (slug) WHERE slug IS NOT NULL`); Postgres only infers an arbiter index whose predicate
matches the `ON CONFLICT` clause, so the statement raised *"there is no unique or exclusion
constraint matching the ON CONFLICT specification"* on every conflict — the exact case the guard
exists to absorb. Verified empirically against the dev database (`{ target }` → error;
`{ target, where: isNotNull(projects.slug) }` → succeeds). The shared module now supplies the
predicate, with a comment explaining why.

project-less tasks with `.set({ deletedAt: now, leadId: null })`. That nulls the last remaining
anchor, and `tasks_anchor_present` is a row-level CHECK that ignores `deleted_at`, so the update

lead-only task has no other home. Project tasks that merely reference the lead keep their project
anchor and are untouched, which is why the FK stays `SET NULL` rather than `CASCADE`.

**Scope note — the `/my/tasks` board.** The board is built by hydrating project graphs
(`fetchProjectsWithRelationsByIds`) and grouping tasks beneath them; `MyTasksInitialEntry.projectId`
is a required string. A project-less task has no group to join, and inventing a synthetic
"Lead tasks" project is a grouping decision §04 does not specify. Lead tasks are therefore excluded
from that board and reach the assignee through the **dashboard My Tasks widget**, which renders a
flat list and shows them with a "Lead" label. The data layer (the part W18 is actually about) returns
them everywhere.

**Regression avoided.** Making `project_id` nullable initially broke opening a lead task at all:
`resolveTaskInit` resolves a task through its project graph and 404s without one, so every lead task
would have become un-openable — worse than before §04, where they all carried the Sales project.
`fetchLeadTaskWithRelations` hydrates a project-less task using the *same* relation loaders as the
project path, rather than a second definition of "task with relations".
