# PRD 003 — Architecture Review

Audited 2026-08-07 (principal-engineer pass verified against code; product pass against
placetostandagency.com). Every finding below is **resolved** — section files incorporate the
resolutions inline; codes (C#, W#, I#, PW#, PI#) are referenced from section files, PROGRESS.md,
and TEST-PLAN.md.

## Critical

| # | Section | Finding | Resolution |
|---|---------|---------|------------|
| C1 | 01 | My Tasks resolves tasks **client-side only** against the assigned-task set (`listAssignedTaskSummaries` → `buildTaskLookup`); there is **no by-id fetch**. A task created in a project with no tasks assigned to the selected assignee leaves the sheet in create mode with the new id in the URL — a second save duplicates. | **Owner decision:** the My Tasks server page fetches the URL's active task (+ its project with relations) by id when it isn't in the assigned set and merges it into `projects`. Also future-proofs task deep links. |
| C2 | 01 | Proposed `handleTaskCreated` cleared `createTaskContext` **before** `router.push`; the render-time re-sync (`my-tasks-page.tsx` ~L99–107) then flips `isSheetOpen` false and arms the 300ms unmount before the URL lands. | Gate the re-sync with a `justCreatedTaskIdRef` (or push first and clear context once `activeTaskId === createdId`). Section 01 updated with the exact sequence. |
| C3 | 01 | On the board, `handleEditTask` sets `routeTaskId` + `pendingTaskId` before navigating (`pendingTaskId` stops the sync effect from closing the sheet), and the sync effect only sets `sheetTask` when the task is found in `projects` — the fresh task isn't there until refresh lands. A bare `navigateToProject` leaves the sheet closable/in create mode for one refresh cycle. | `handleTaskCreated` mirrors `handleEditTask` (set both ids) and optimistically keeps the current form values until the refreshed `task` prop arrives. Section 01 updated. |
| C4 | 01×02 | The time-log mutation's `router.refresh()` now fires **while the task sheet is open**; fresh props re-trigger the reset chain (the open-effect re-fires whenever `resetFormState` identity changes → whenever `defaultValues` → `task` changes), wiping unsaved task-form edits — and 01's originally proposed extra reset effect would **double-reset**. | One consolidated re-baseline rule: reset only when `task?.id` **changes** (create→edit arrival or different task), never on same-id identity changes. Audit the existing open-effect's dep chain when implementing; do not add a second competing effect. |
| C5 | 02 | Create-mode pre-link as originally specced fails three ways: programmatic `open` doesn't fire Radix `onOpenChange`, so seeding at `handleDialogOpenChange(true)` never runs; seeding selection without `baselineState.taskIds` makes an untouched dialog instantly dirty (discard confirm on close); and `eligibleTasks` filters out accepted/archived/deleted tasks, silently unselecting the pre-linked id. | Dedicated effect keyed on `open && !isEditMode` seeds **both** selection and baseline. **Owner decision:** the pre-linked task bypasses the eligibility filter (locked/selected chip) so accepted tasks can take hours from their own sheet; archived/deleted tasks disable the button instead. |
| C6 | 02 | No reusable hydration path exists — linked-task hydration is inline in `listProjectTimeLogs` (~L118–178) and must be extracted before a by-task query can share it. The inline query also **misses `isNull(timeLogTasks.deletedAt)`** — a latent live bug: soft-deleted links flow into `linked_tasks`, so the edit dialog re-selects previously unlinked tasks. | Extract `hydrateTimeLogEntries(logIds)` first; add the missing `deletedAt` filter in the shared path (deliberate bug fix — noted in TEST-PLAN regressions since it changes Time Logs tab edit behavior for affected logs). |
| C7 | 01 | `form.reset(form.getValues())` re-baselines the form only; `useUnsavedChangesWarning` is fed `isDirty \|\| attachmentsDirty`, so after an edit save with touched attachments the discard prompt still fires. | Save success also calls `resetAttachmentsState({ preservePending: true })`; verify `useTaskAttachments` behavior across the create→edit remount. |

| W7 | 03 | Two removal ranges are **non-contiguous**: `projects-board-tabs.tsx` scope entries interleave with `activityDisabled`/`reviewDisabled`/`timeLogsDisabled` (L44/48/49, L101/105/106, L159/163), and `use-projects-board-navigation.ts` L58–64 contains those three live props at L61–63. | W9 | 04 + PW2 | Widened list is unbounded — every COMPLETED/ON_HOLD project for every client rides the RSC payload, and a long-lived client's hover card could be 80 items tall. | `max-h-80 overflow-y-auto` on the total card's list; payload growth accepted (single query, page is admin-only); noted as acceptable by product review since long histories are the *valuable* case. |
| W10 | 05 | Proposed `lib/settings/users/constants.ts` collides conceptually with the existing `lib/settings/users/state/constants.ts` (dialog/table-state constants) — two `constants.ts` one directory apart. | New file named **`apps/internal/lib/settings/users/filters.ts`** instead. |
| W11 | 05 | `import { userRole } from '@pts/db/schema'` is off-convention — every app-side consumer (incl. the cited `form-submissions/constants.ts` precedent) imports via **`'@/lib/db/schema'`** (the one-line re-export). | Snippet corrected. | W12 | 05 | AC said the access toggle causes no immediate row removal under `access=enabled` — **wrong**: `use-set-user-disabled-action.ts:77` calls `router.refresh()`, so the row vanishes on success. | AC reworded: immediate server-driven removal is the correct, expected behavior. |
| W13 | 01 | Create→edit swaps `editorKey` (`'new-task'` → `task.id`) and `historyKey`, remounting the TipTap editor and resetting undo history mid-session. Expected, but was implicit. | Explicit acceptance criterion + test item: content preserved (it's in the saved task), undo stack cleared. |
| W14 | 02 | Global React Query defaults set `staleTime: 60_000`; "keep staleTime 0" silently wouldn't happen. | `staleTime: 0` set explicitly on the query. Closest pattern: `use-project-time-log-history.ts`. |
| W15 | 01 | `defaultProjectId` on My Tasks is `createTaskContext?.projectId ?? editingTaskMeta?.project.id ?? null` — clearing context before the task resolves feeds a reset with `null` project. | Covered by C2's gating: context is cleared only once the created task resolves. |
